# MIG-008 Design — Guardian release manifest and immutable watchdog

Candidate base: `6a1917630d6b4763f51f00b15d19db30c253505c`.

Acceptance: **Independent watchdog validates artifact identity, approvals,
STOP, compatibility and rollback.**

This design reuses the existing `tools/astra_watchdog.py`,
`src/jarvis_v2/guardian/release.py`, `src/jarvis_v2/guardian/rollback.py`,
the deterministic Master upgrade tables and the existing owner-approval
workflow. It does not create a second controller, change `main`, or grant a
model authority over its own release.

## Authority and non-goals

| Concern | Authority | Non-goal |
| --- | --- | --- |
| Candidate implementation | Main Codex builder | Watchdog does not write application code |
| Candidate QC and child receipts | Independent QC and Master | Manifest booleans are not proof by themselves |
| Owner approval | Authenticated Master approval receipt | Model output cannot satisfy the gate |
| Release pointer and one-writer fence | External watchdog plus Master lock | Guardian AI cannot switch its own pointer |
| Read-only inspection | `guardian.release.inspect_canary` | It does not deploy, sign, or route traffic |
| Recovery | `guardian.rollback` and watchdog | Never delete the candidate or historical state |

The watchdog is a separate, minimal process. It may inspect canonical state,
verify a candidate and activate a previously tested fast-forward pointer under
the exact gates below. It never clears STOP, PAUSE or quota markers and never
starts coding workers.

## Release manifest contract

The existing `jarvis-v2.release-candidate/1` manifest remains the stable
boundary. Required fields are:

```text
schema
module
artifact
sha256
candidate_sha
base_sha
previous_healthy_artifact_sha256
external_watchdog_identity
gates.independent_qc
gates.tests
gates.security
gates.rollback_ready
gates.owner_approved
gates.watchdog_ready
evidence_refs.independent_qc
evidence_refs.tests
evidence_refs.security
evidence_refs.rollback
route_gate.mode = inactive
route_gate.single_writer_fenced = true
```

The artifact path is relative to the manifest, cannot escape its directory,
cannot be a symlink, and must hash to `sha256`. `candidate_sha` and `base_sha`
must be full Git commit IDs. The candidate must be a fast-forward descendant
of the recorded rollback/source checkpoint.

`gates.owner_approved` is an assertion that the Master has a verified,
task-bound owner receipt; it is not a self-attested permission. The watchdog
must receive the Master-validated evidence reference and reject an absent,
stale or mismatched approval. `guardian.release.inspect_canary` remains a
read-only structural/checksum check and must not be described as a signature
verifier.

## Activation sequence

```text
PROPOSED
  -> PATCH_IN_ISOLATION
  -> TESTED + BACKUP + CANARY + HEALTH checks
  -> DRAIN_NEW_CLAIMS
  -> verified SQLite backup and Master-lock fence
  -> STAGED_CANARY with route closed
  -> external watchdog validation
  -> fast-forward pointer/checkpoint switch
  -> HEALTH_SOAK
  -> COMMITTED or deterministic rollback
```

Before the pointer switch, the watchdog must verify:

1. Canonical SQLite integrity is `ok` and the configured integration path is a
   clean worktree whose HEAD equals the recorded integration SHA.
2. The upgrade row is activation-ready and every required check is PASS.
3. The candidate and rollback commits exist and `base/rollback` is an ancestor
   of the candidate.
4. No active task/lease or competing Master prevents the short activation
   fence.
5. `STOP`, `PAUSE` and `PAUSED_QUOTA` are absent only because the owner has
   not requested a stop; if any marker is present, activation fails closed.
6. The route is inactive and the single-writer fence is true.
7. The last-known-good database backup passes SQLite integrity and its digest
   matches the activation journal.

The pointer switch and integration checkpoint are recorded with the batch ID,
previous SHA, candidate SHA, backup path/digest, current HEAD and activation
receipt. The old artifact and backup remain available for rollback.

## Rollback sequence

If canary or health soak fails, the watchdog records `ROLLBACK_PENDING`, keeps
the failed candidate for diagnosis, verifies the last-known-good artifact and
restores only the compatible target/checkpoint. It then records the rollback
receipt and leaves the system in a safe, fenced state. A healthy canary cannot
trigger rollback, a tampered last-known-good artifact is rejected, and unsafe
paths are rejected before any write.

Rollback is not a release approval and does not mark a task complete. The
Master must reconcile the resulting integration SHA and receipts before new
claims resume.

## Compatibility and failure behavior

Compatibility is checked against the recorded component schema, SQLite schema
version, source/integration ancestry and required module contracts. A schema
or ABI mismatch must remain staged or roll back; the watchdog must not perform
an unreviewed migration during activation. Invalid manifests, missing evidence,
dirty worktrees, active controls, competing locks, missing backups and stale
approval references fail closed with bounded audit metadata only.

## Test and evidence matrix

| Requirement | Existing deterministic evidence | Required result |
| --- | --- | --- |
| Artifact identity and path safety | `tests/test_guardian_release.py` | Hash/path tampering rejects canary |
| Declared QC/security/rollback gates | `tests/test_guardian_release.py` | Missing evidence rejects canary |
| Closed route and one-writer fence | `tests/test_guardian_release.py` | Active/extended route rejects canary |
| STOP/PAUSE/quota preservation | `tests/test_astra_watchdog.py`, `tests/test_guardian_standby.py` | Activation/start is refused; marker remains |
| Fast-forward and checkpoint recording | `tests/test_astra_watchdog.py` | Candidate advances only through verified ancestry |
| Last-known-good rollback | `tests/test_guardian_rollback.py`, `tests/test_astra_watchdog.py` | Failed canary restores healthy artifact and preserves state |
| Restart/crash budget | `tests/test_guardian_restart.py` | Repeated failure escalates without duplicate replay |
| Independent controller boundary | `docs/operations/GUARDIAN_RELEASE.md` and watchdog source | Watchdog cannot self-approve or start coders |

Hosted CI, production deployment, a native-device soak and owner signing are
separate acceptance gates. Local tests do not substitute for them.

## Scope and next implementation boundary

MIG-008 is a design deliverable. It defines the existing interfaces and the
evidence required before activation; it does not install a production service,
switch a release route or alter owner/security policy. Any missing signature
binding or schema migration must be implemented in a later scoped task with
independent QC, verified backup and watchdog canary evidence.
