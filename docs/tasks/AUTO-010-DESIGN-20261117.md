# AUTO-010 design — actionable notifications and deduplication

## 1. Scope and traceability

| Requirement | Design decision | Later evidence |
| --- | --- | --- |
| No duplicate notices | Stable notice identity and a unique D1 constraint on rule, source event and policy version | Replay test and concurrent insert test |
| Disabled rules respected | Evaluate `enabled` and effective time window before creating a notice or delivery row | Disabled-rule negative test |
| Approval before outbound action | Rule selects `none`, `owner_review` or `owner_signed`; delivery is not eligible until the required decision is verified | Approval and expiry tests |
| Cloudflare is coordination only | Store bounded metadata and delivery descriptors; never execute host commands or local inference | Permission and payload tests |
| Existing event architecture reused | Consume the versioned Backend event envelope and its idempotent delivery receipts | EventBus integration test |
| Existing authorization reused | Use the Backend capability and owner-approval boundary; do not create a second approval authority | Authorization binding test |

Dependencies are `AUTO-005` (durable scheduling) and `AUTO-009` (metadata/audit
boundary). The design is documentation-only; it does not claim a deployed Worker,
configured D1 database or an authorized outbound delivery channel.

## 2. Versioned contracts

### Notification rule `archon.notification-rule/1`

```json
{
  "schema": "archon.notification-rule/1",
  "rule_id": "automation.deadline.v1",
  "event_type": "task.deadline_due",
  "module": "automation",
  "severity": "high",
  "enabled": true,
  "active_from": "2026-01-01T00:00:00Z",
  "active_until": null,
  "dedup_window_seconds": 3600,
  "approval_class": "owner_review",
  "delivery_channels": ["approved_dashboard"],
  "policy_version": 1
}
```

Rules are owned by ATLAS/automation and are immutable by event producers. Unknown
schema versions, modules, severity values, channels, approval classes, duplicate
channels and invalid time windows are rejected. A disabled or out-of-window rule
produces no notice row and no delivery effect.

### Notice `archon.notification-notice/1`

```json
{
  "schema": "archon.notification-notice/1",
  "notice_id": "stable-operation-id",
  "source_event_id": "event-id",
  "rule_id": "automation.deadline.v1",
  "policy_version": 1,
  "state": "approval_required",
  "severity": "high",
  "occurred_at": "2026-01-01T00:00:00Z",
  "expires_at": "2026-01-01T01:00:00Z",
  "summary_code": "deadline_due",
  "reference_ids": ["TASK-001"],
  "payload_hash": "sha256-of-approved-metadata"
}
```

`notice_id` is derived from the source event identity, rule identity and policy
version. The payload contains fixed summary codes and bounded references only; it
does not contain source text, task packets, private documents, conversation data,
credential values or model output.

### Delivery receipt `archon.notification-delivery/1`

```json
{
  "schema": "archon.notification-delivery/1",
  "notice_id": "stable-operation-id",
  "channel": "approved_dashboard",
  "state": "pending",
  "attempt": 0,
  "effect_hash": "",
  "updated_at": "2026-01-01T00:00:00Z"
}
```

The unique key is `(notice_id, channel)`. A completed receipt is idempotent; a
failed receipt is retryable only while the notice is unexpired and the approval is
still valid. The delivery adapter receives a bounded notice, not the originating
event payload.

## 3. State sequence

```text
event received
  -> validate schema, scope and sequence
  -> load enabled rule set
  -> reject disabled/out-of-window rule
  -> compute notice_id and insert-or-return existing notice
  -> approval_required | ready
  -> create one delivery row per approved channel
  -> fenced delivery receipt
  -> sent | acknowledged | failed | expired
```

The insert and dedup lookup occur in one transaction. Replayed events return the
existing notice and do not create a second delivery row. A notice never bypasses
an owner decision by changing its state locally; an expired, revoked or mismatched
decision remains blocked.

## 4. Safety and failure matrix

| Condition | Deterministic result | Recovery |
| --- | --- | --- |
| Rule disabled | No notice; record bounded audit code | Re-evaluate on a later event or rule version |
| Duplicate event | Existing notice returned | No new delivery effect |
| Disabled channel | No delivery row for that channel | Owner-approved rule update |
| Missing approval | `approval_required` | Wait for the exact bound decision |
| Expired approval or notice | `expired` | New source event or approved policy version |
| Invalid event/scope | Reject before persistence | Correct producer contract |
| D1 unavailable | Preserve source event retry state | Bounded retry/dead-letter path |
| Delivery failure | Receipt `failed`, no false success | Retry with fence while valid |
| STOP/PAUSE | Do not create new external effects | Resume only through ATLAS controls |
| Unknown channel or schema | Fail closed | Versioned implementation and review |

No notification adapter may execute a host command, wake a device, change a
credential, trade, send a financial instruction or deploy a release. Those actions
remain separate owner-approved capabilities.

## 5. Acceptance test plan

| Test | Expected result |
| --- | --- |
| Enabled rule receives one event | One notice and one pending delivery |
| Same event is replayed twice | Same notice receipt; no duplicate delivery |
| Two consumers race on one delivery | One effect fence; the other receives an in-progress result |
| Rule is disabled | No notice or delivery row is created |
| Rule is outside its active window | No notice is created |
| Approval digest is wrong or expired | Notice remains `approval_required` |
| Approved channel is revoked | Delivery is refused and recorded as blocked |
| Invalid scope or unknown schema | Input is rejected without persistence |
| D1 retry after commit | Idempotent read returns the original notice |
| Notice expires during retry | No outbound effect; receipt becomes `expired` |
| Payload contains prohibited fields | Boundary rejects it before storage |
| STOP/PAUSE is active | No new delivery effect is attempted |

Hosted Worker/D1 execution, actual outbound channel delivery and retention jobs
are separate host qualifications. Local tests must not be reported as hosted
success.

## 6. Ownership, rollback and implementation boundary

The later implementation should reuse `EventBus.publish/pending/deliver` and
`AuthorizationServer` rather than adding a parallel ledger or approval service.
Cloudflare should persist only the notification tables and safe metadata needed for
the approved coordination role. Schema changes must be additive, backed up and
tested on a disposable copy before activation.

Rollback is a versioned policy change: stop new claims, let in-flight delivery
receipts settle, preserve the old rule/policy version, and restore the last-known-
good Worker and schema checkpoint. Never delete prior notices or receipts to make a
rollback appear clean.

The future implementation paths are limited to `src/jarvis_v2/automation/`,
`infra/cloudflare/` and their focused tests. This design artifact itself is the
only change in this generation.

## 7. Supervisor review checklist

- [ ] Event type, module and privacy scope are validated before rule evaluation.
- [ ] Disabled and out-of-window rules cannot create notices.
- [ ] Notice and delivery identities are deterministic and unique.
- [ ] Owner decisions are exact, digest-bound and expiry-checked.
- [ ] Delivery is independently fenced and idempotent.
- [ ] Payloads contain only bounded approved metadata.
- [ ] STOP/PAUSE and capability revocation remain authoritative.
- [ ] Retention, dead-letter and hosted Worker behavior have real evidence before release.
- [ ] No new approval authority or second task ledger is introduced.
