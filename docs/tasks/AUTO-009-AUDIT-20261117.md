## Findings

### Storage and replay

`schema.sql` stores only bounded run and event metadata. `event_id` is the event
primary key and `(run_id, seq)` is unique. The Worker uses `INSERT OR IGNORE`
for event replay and only advances the visible run row when the incoming sequence
is newer. These controls prevent duplicate timeline entries and out-of-order state
rewinds in the inspected implementation.

### Redaction and input bounds

The ingestion validator requires the exact fourteen-field event shape. It accepts
stage, step, branch, base revision, bounded counters, result text and timestamps;
it does not accept source text, task packets or model conversation fields. The
request body is capped at 4096 bytes, result text at 100 characters, and numeric
fields have explicit safe bounds. The D1 schema comment and Worker contract both
define the feed as metadata-only.

Separate ingest and view authorization values are required. The inspected files
contain no configured authorization value. The dashboard returns bounded rows and
does not return a raw terminal or model transcript.

### Public/private export

The existing monitor exposes an authenticated summary, recent runs and a bounded
event timeline. The summary is aggregate status data; run and event rows require
the view authorization. This is a metadata export, not a source or conversation
export. The implementation does not expose a public event or run payload route.

### Retention and unresolved gaps

No D1 TTL column, scheduled purge, retention window, dead-letter policy or deletion
receipt was found in the inspected schema or Worker. The `LIMIT 50` and `LIMIT
100` query bounds limit one response but do not delete old records. The inspected
tests cover authentication, payload rejection, idempotent replay and sequence
ordering, but do not test retention expiry or purge behavior.

No configured D1 binding or deployed Worker was available in this worktree, and the
TypeScript dependencies were absent (`node_modules` was not present). Therefore
live-host retention and hosted export behavior remain unverified.

## Decision and follow-up

The metadata storage, input-boundary and authenticated export portions are present
and bounded. Retention is an identified implementation gap, not a passing claim.
A later implementation task must define the owner-approved retention window,
idempotent purge, dead-letter handling, deletion evidence and no-network tests
before hosted retention can be accepted. This audit intentionally made no source,
database, service or external-environment changes.
